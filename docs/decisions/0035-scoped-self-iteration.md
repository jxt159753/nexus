# ADR 0035：范围预授权的高自由度自迭代

日期：2026-10-23。状态：**提议（Proposed），仅完成方案文档，尚未批准实施或启用。** 用户要求制定插件、Skill、Core/Node 源码的自动修改、验证、发布与回滚方案，尽量减少人工确认，并明确权限边界。技术细节集中在[架构第 20 节](../ARCHITECTURE.md#self-iteration-design)，任务与状态只见 [M9 路线图](../ROADMAP.md#m9-self-iteration)。

## 背景

既有插件已有不可变版本、独立契约测试和 full 自动启用，Skill 有固定步骤及原 Harness；Core/Node 已有单活、持久回执和固定包部署基础。尚缺可衡量改进、持续修订、源码隔离、可信发布控制器和自动回退的完整闭环。样例测试通过、目标标记 complete 或模型自述成功都不足以授权自动升级。

同时，当前宿主 Shell/插件按 Node 当前用户执行；Core 内部模块共享进程与数据库访问能力。只限制可编辑文件名、增加提示词或复用 full 不能形成“候选不能改变权限和裁判”的可靠边界。

## 提议的决定

1. **一次范围授权，逐动作确定性核对。** 新增与 normal/full 正交的 owner 自迭代策略，分别绑定目标、可修改对象、资源/数据/外发、发布方式、验收、期限和有界配额。owner 可显式选择持续至撤销；每个改进单和执行许可仍有限。范围内候选、测试、普通版本发布与回退自动推进，只记录具体摘要授权，不逐次弹窗。full 本身不授予源码发布权。
2. **可自动修改整个获准源码副本，自动发布按信任域分层。** 插件、Skill 和已隔离的 Core/Node 业务组件可在门禁通过后自动发布；与身份、权威状态、凭证、回执或部署控制同信任域的代码，自动产出候选和完整验证，发布需 owner 批准具体摘要。先提取/隔离可演进组件才能扩大自动发布范围，不把现有目录结构当作隔离证据。
3. **保持一个决策中心。** Core 独占目标、任务、授权、模型账本和记忆。复用现有 Node/Sandbox 执行候选工作；隔离业务计算进程只处理有界请求，不形成第二规划循环。独立评测器只计算证据；发布器只执行固定部署事务和最小恢复，不调用模型、不创建目标、不改业务终态。
4. **裁判、发布器与运行身份受操作系统保护。** 开发执行、自动演进业务组件、可信 Core/Node 控制部分、发布管理使用分离权限。拒绝任意 Shell/MCP/动态加载通道绕过；开发端不能修改裁判、发布策略、密钥或权威数据。可信控制部分的运行依赖与启动路径同样受保护。首次建立这些边界是后续需明确批准的实施工作。
5. **固定候选与独立评测。** 验收在修改前定义，基线与候选在同环境比较；可信回归集、真实进程/设备结果及数据恢复证据决定晋级。模型评审和候选自带测试仅为补充。源码、产物、环境、策略或基线改变使旧证据/许可失效；失败不重测到偶然通过。
6. **单活停机切换与兼容回退。** Core 先排空、维护、一致备份、停旧，再由受保护发布器切换固定包并暂停验证。Node 由外置启动器更新，保留身份与回执。插件/Skill 依赖成组切换，旧运行不混用版本。自动回退优先只切程序并保留当前数据，不恢复旧授权、未知费用或未知执行。
7. **数据恢复独立处理。** 首批自动发布不含迁移；以后仅允许已准入并验证双向读写兼容的前向模板。破坏性迁移与备份覆盖需具体批准。不能把新增列、备份存在或程序能启动当作可回退的证明。
8. **停止权和失败收敛优先。** 次数、时间、空间和失败阈值由可信配置约束；重启、分段和子任务不重置根账本。只有显式授权自动续跑且旧执行/费用可核对时继续。未知先对账，回退失败保留维护状态并通知；停止/撤销不能被自迭代重写或规避。

## 取舍

- 不采用“full 加大循环次数即可自升级”：它不能解决独立验收、同进程绕过、数据兼容和核心进程失效后的恢复。
- 不要求每个插件/Skill/普通组件版本都人工确认：owner 授权范围与确定性门禁负责常规迭代，只有扩大边界或可信变更集中到固定候选确认。
- 不采用生产双 Core 蓝绿切换：会改变单活权威并增加重复派发风险；候选只在独立测试数据和身份上运行，生产允许事先约定的有限停机。
- 不引入第二套代理平台、消息中间件、插件目录或记忆服务。必要新增仅是 Core 内的改进记录、受保护评测与跨停机发布/恢复能力；现有表和执行协议优先复用。
- 保护边界会使一部分 Core/Node 修改仍需人工发布确认。该限制明确表达当前同信任域代码的风险，不声称任何测试或目录白名单能保证任意自改代码安全。

## 与既有规则的关系

本提案不立即替代 ADR 0014 的旧 Tool/Skill 版本批准、ADR 0028 的插件 normal/full、ADR 0034 的原生 Skill/MCP，以及普通聊天的逐轮外发和显式恢复规则。后续只有实现、验证并由 owner 启用新策略的对象采用新流程；旧记录/批准不回填，前端继续由用户直接控制 DSH。金额限额沿用 ADR 0032 的 owner 选择，不因本方案重新开启；次数、审计、价格有效性、取消和未知边界保留。

## 技术依据与验证责任

- Git worktree 提供多个工作树并共享部分仓库管理数据；本方案因此不将 worktree 当作执行隔离。[Git 官方说明](https://git-scm.com/docs/git-worktree)
- Python 明确指出 Python 层审计钩子不适合实现安全沙箱；本方案不依赖提示词、import 限制或钩子隔离不受信代码。[Python 官方说明](https://docs.python.org/3/library/sys.html#sys.addaudithook)
- Windows 进程访问由安全上下文和访问权控制；分账户、令牌/ACL 与进程访问隔离必须以真实机器验证。[Microsoft 官方说明](https://learn.microsoft.com/en-us/windows/win32/procthread/process-security-and-access-rights)
- SQLite 在线备份可生成一致快照，但快照不包含其后发生的业务事实；本方案把一致备份与无损回退分开。[SQLite 官方说明](https://www.sqlite.org/backup.html)

以上仅为设计依据，不表示 NEXUS 已实现账户隔离、可信评测、自动源码发布或故障回滚。对应实施验收全部保留在路线图。
