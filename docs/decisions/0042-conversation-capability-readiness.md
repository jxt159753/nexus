# ADR 0042：会话能力的真实可用性与 MCP 接通

日期：2026-10-24。状态：按用户要求采用并部署；结果见 [P83](../ROADMAP.md#p83-windows-mcp) 与[验证记录](../WINDOWS-MCP-VERIFICATION.md)。补充 ADR 0034/0037，不授权 Core/Node 自行修改源码或发布。

## 决定

能力判断同时使用 Core 已部署契约、具体 Node 的执行器配置、完整配置摘要及身份/资源权限。插件注册表不是可执行状态。`plugin_inspect` 返回执行条件和具体阻塞，`get_node_status` / 节点接口给出插件配置状态；模型先检查相关插件，不再套用“没有 Shell、安装或生成能力”的静态结论。普通/完全模式仍由 owner 控制，full 不能解决执行器未配置或信任摘要不一致。

沿用 Shell 安装、MCP 登记/发现/调用、Skill 候选/测试/批准的已有链路，不新增无限权限安装器。安装先固定包版本与设备位置；后台 job 使用所属会话的 `builtin.jobs/job_output` 对账，真实退出及停止证据成立后才登记。Core 管配置/目录修订，Node 启动实际 stdio 程序，发现验证后才激活。MCP 查询可返回未登记、pending、failed 及最新修订；这不使失败版本可执行。Windows 路径在协议中统一正斜杠以保持跨平台命令摘要。FastMCP 的布尔 `x-fastmcp-wrap-result` 仅作为 schema 注解忽略，字段及结果类型继续校验。

Skill 批准仍绑定确切版本、设备、测试及策略期限。跨设备目录按设备条目查找固定版本，不能借另一设备的版本可见性或批准执行。原生步骤的 MCP `isError:true` / Shell 非零退出使流程失败，保存已校验的底层结果、失败步骤与任务引用，并在原结果外发授权内交回模型；不把协议成功当业务成功，也不把笼统失败推断为版本/目录摘要不符。Windows-MCP 的 `USER_CONTROL` 是用户优先让权，不能通过关闭保护恢复执行。

## 有界容量

安装、核验、登记、调用和候选创建需要多次独立检查。新增 owner 配置 `models.chat_work_max_actions`，默认4、最大16；每轮最多动作数加一次模型收尾交换，每批仍最多4个函数。`models.chat_input_bytes` 默认32768、最大65536。当前生产设置16动作/17交换和65536字节；模型无权修改。迁移034只扩展 `chat_work_steps.step_index` 的约束，保留原记录、外键及索引。自动记忆开关也进入完整请求大小计算，准入和实际发送使用相同选项。

参数诊断根据已声明字段返回有界路径及确定性修正提示，不回显原始参数/异常。调用次数、超时、外发、取消、恢复 hold、费用记账和静态能力交集保持。审批有效时不因会话变化重复批准同一 Skill；新增版本、到期或策略变化仍重新核验。

## 发布与限制

以实际线上 wheel 为固定基线，只覆盖列明后端资源；启动前验证 systemd 最终生效的 ExecStart，避免历史 drop-in 遮盖候选。Core/Node 配置和完整信任摘要配套核对，Windows 原生入口拒绝“允许 plugin.call 但执行器未启用”的不一致配置。备份、单活切换、历史摘要核对和数据库副本兼容回读保留。

stdio 每次操作独立进程，不承诺 Snapshot 标签等内存状态跨调用保留。有限 schema 支持、10秒工具时限、输出大小、桌面用户活动及第三方变更仍可能使调用失败。真实模型测试证明列明路径可执行，不保证每轮都作出最佳判断，也不代表所有第三方 MCP 都已兼容。
