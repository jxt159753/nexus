# 目标验收、持续工作与运行治理

本文件说明后端契约、使用边界和交给 DSH 的接入要求。批准范围、实际验证和上线状态只在 [P81 路线图](ROADMAP.md#p81-autonomy)维护。设计取舍见 [ADR 0041](decisions/0041-evidence-bound-autonomy.md)。

## 目标与证据

`builtin.goal` 1.1.0 复用原目标、聊天工作轮、Harness 任务和费用账本。目标创建后先定义 `goal_plan`，每个步骤通过 `goal_checkpoint` 保存进度；`update_goal(status=complete)` 重新核对全部条件，才设置 `completion_verified=true`。

验收是**已声明断言的机器核对**，不是任意业务质量、宿主安全或用户验收。界面显示 `verification=declared_task_assertions`，不能显示“用户已验收”。模型生成的验收条件可能不完整，owner 应检查是否覆盖真实目标；若原始条件错误，停止旧目标并按正确条件建立新目标，保留原记录。

计划的最小示例（真实 `goal_id` 使用已有会话目标）：

```json
{
  "expected_revision": 0,
  "constraints": ["只操作本任务 workspace，保留原始输入"],
  "criteria": [{
    "id": "report",
    "description": "报告内容与预期一致且读取未截断",
    "category": "artifact",
    "tool": "filesystem.read",
    "arguments": [{"path": "/root_id", "equals": "workspace"}, {"path": "/path", "equals": "report.txt"}],
    "assertions": [{"path": "/text", "equals": "检查通过"}, {"path": "/truncated", "equals": false}]
  }],
  "steps": [{"id": "readback", "instruction": "执行文件读回并核对报告", "depends_on": [], "criteria": ["report"]}]
}
```

`path` 是 JSON Pointer，`arguments` 作用于任务动作的参数，`assertions` 作用于持久化任务结果。`category` 区分 `artifact`、`test`、`effect`，不会赋予额外验证能力。文件可绑定路径和 SHA-256，程序可绑定具体测试命令、退出状态和结构化结果，实际效果需独立查询/读回。非空参数工具必须提供参数断言。

证据必须属于本目标根工作轮或其续跑轮，关联到当前有效 `attempt_id`；任务成功、结果已知、验证器记录存在、执行已停止，并且断言全部一致。其他会话的任务、早于目标的任务、只含模型成功声明、仍在运行或 `unknown` 的结果都不能作为完成证据。保存的证据包含任务、尝试和内容摘要；完成时再次核对，不能替换原结果后沿用旧证据。核对表示证据采集时的观察，不能保证外部世界之后永不变化。

## 依赖、检查点与恢复

- 每个计划最多 12 条条件、16 个步骤、8 条约束，总 JSON 不超过 7,000 UTF-8 字节；依赖必须无环。约束总长 800 字，未完成事项总长 1,000 字。
- 已完成和运行中的步骤定义不可替换；重新规划保留尝试身份、成功证据和原始验收条件，不能改名来重做相同步骤。最多 3 次重规划，每次需说明原因；每目标最多 100 个检查点。
- 同一个用户工作轮只能建立一个目标；自动续跑轮不能另建目标来重置轮数、期限或根预算。新目标需要新的用户工作轮，既有目标用原状态与重规划接口继续。
- 成功检查点须满足全部依赖和本步骤条件；有前置依赖的步骤，其证据任务必须创建于前置成功检查点之后，不能拿依赖完成前的旧读数充当后续效果。连续 3 个工作轮没有已核实进展时暂停，不因反复记录“失败”重置计数。原目标轮数、期限、模型次数/费用、取消及未知执行边界继续生效。
- 每段续跑携带目标和持续约束，要求先读取完整计划、最近检查点、证据和未完成事项。`get_goal` 返回步骤状态、最近 3 个检查点摘要、绑定任务与观察订阅；`get_goal(step_id=...)` 读取指定步骤的最近完整检查点及未完成事项，即使它已不在最近3条中。owner详情保留完整检查点字段；更早记录仍持久保存。
- `resume_after_restart` 默认关闭，只能由 owner 接口设置。开启后仍检查身份、模式指纹、节点范围、取消游标、目录版本、根预算，以及上一段和相关副作用是否已结算。中断中的未知模型请求/任务不会自动重发。
- 提交续跑与保存结果间崩溃时，按原 `request_id` 查找已落盘工作轮，只补记一次轮数与步骤关联。未提交完成的续跑保留中断状态，暂停等待核对。

这些机制避免重复派发同一执行身份并保留已完成工作。不同任务参数表示新的动作，依然要由原权限与执行验证处理；不能宣称语义相似的任意操作都能自动识别为重复。

## 持续上下文

会话搜索在同 owner、同项目和未归档会话中，最多检查最近 200 个完成轮；响应有长度和条数限制。带逐轮记忆、引用或附件的内容继续走原预览/同意流程。自动记忆引用还要通过当前持续授权 revision 和有效期检查，撤销后的旧历史不会通过搜索结果重新流入模型。

目标计划、检查点和调度提示也可能派生于这些内容。续跑及模型读取目标前，会核对原根轮和全部已关联续跑轮的来源同意；自动记忆撤销/变更会暂停相关续跑，逐轮私密引用不能自动沿用到下一轮。原授权轮内的处理仍可继续，owner 界面仍可查看自己的记录；不能通过读取目标记录绕过新的外发同意。

任务约束、依赖、证据和未完成事项使用目标记录保存，不把它们冒充个人长期记忆。P79 的保存/外发同意范围保持不变。

## 独立业务用例与插件回退

owner 为 `user.*` 插件维护独立业务用例；模型可读取测试结果和生成新候选，不能通过模型工具改写该用例集。每套最多 4 个用例、12 KiB，使用现有 `PluginCase` 的 `tool/input/expected/files`，有独立 revision 和 digest。

测试冻结候选、独立用例、原启用基线和环境。候选原契约样例、候选业务用例、基线同一批业务用例分别记账并比较。配置业务用例后，批准/启用新版本必须有当前 revision 的通过证据；仅原样例通过不够。修改用例使旧测试凭证失效，但不会擅自执行测试或改用户当前启用版本。

`rollback_on_failure` 默认关闭。owner 开启后，新旧工具契约与依赖必须一致、基线必须通过同批业务用例，才能进入观察。观察只针对授权会话中该固定候选的真实任务；已知失败或实际输出偏离对应业务用例时，先停用候选，等待该版本的执行全部已知且停止，再恢复仍获批准、环境匹配、未被撤销的旧版本。`unknown` 不直接归咎于候选，也不重做副作用。暂停、取消、会话/身份变化、策略修改或 owner 停用回退版本均会阻止自动恢复。

观察至少 30 分钟且 10 个已结算成功结果后记为 `accepted`；这是观察窗口的技术状态。`host_safety_verified` 始终为 `false`。runsc 内的 SDK 不提供宿主工具调用，Python 宿主代码仍以 Node 当前用户权限运行；样例通过不能证明任意宿主行为安全。回退只切换插件版本，不撤销已经发生的文件、网络或其他外部效果，也不恢复旧数据库。

## 文件、设备与外部事件

owner 创建有范围和期限的 `file/device/task/external` 订阅。文件观察复用 Node 的 `filesystem.read` 与原 Harness 权限，限定 `workspace` 相对路径；设备观察读取认证连接状态；任务观察限定同 owner、同项目；外部事件通过 owner 认证接口提交，标为 `owner_supplied_observation`。未配置第三方账户连接器。

轮询最短 30 秒，每订阅最多 1,000 次、最长 7 天，最多 100 个有效订阅、1,000 个历史订阅、每目标 16 个。每次只处理最多 10 个到期订阅，优先级 0–9。首次读数建立基线，后续变化才生成事件；外部事件用 `source_key` 去重，同键不同内容返回冲突。文件读取使用稳定请求 ID，重启不生成重复执行。

观察本身不调用 LLM。已授权目标用 `goal_wait` 绑定指定订阅；只有该订阅的新事件才生成一次有界续跑，额度仍属于原目标。事件不创建目标、不恢复用户暂停、不放大授权。订阅失效时暂停并给出自然语言说明。通知保存在事件流，由前端读取和确认；不发送邮件、短信或系统外消息。

## 存储和健康管理

只有 owner 已归档、没有活动/未知执行或未结算费用的会话能进入冷存储。先预览摘要，再用相同 digest 提交。正文、模型请求/响应、压缩源和摘要在同一 SQLite 事务中压缩、保存 SHA-256、读回验证后替换热字段；请求身份、原始请求哈希、源摘要、任务、权限和费用账本保留。迁移 032 将源快照的物理搬迁与身份不可变分开；普通 SQL 更新仍不能直接改请求或压缩源。

历史/模型交换 API 自动读回并验证冷数据；取消归档前完整恢复，并重查热容量。损坏时明确拒绝读取，不返回假空历史。每行解压上限 8 MiB，每次归档原文总量 64 MiB，冷数据总量 512 MiB；归档前后都保留身份与审计。

Node 热回执满时，仅压缩 Core 已确认且明确停止的完成/取消回执。旧 `attempt_id` 仍查询冷回执，重传不能再次执行。未知、未停止、未确认回执不移动；冷回执上限 256 MiB，损坏时停止使用该记录。

后台健康服务每 5 秒检查工作协程、热/冷容量、磁盘余量和未知任务。告警仅在状态改变时更新 revision，避免每秒重复通知；工作协程退出、数据库不可用或磁盘不足会阻止新执行。健康 API 反映观察时点，不能证明所有外部依赖或任意协程内部都无故障。

归档释放热历史额度并保留可恢复原件。审计、去重键和受保护记录继续占用真实磁盘；原插件测试、调度事件等独立容量上限仍保留并有接近上限告警。此实现不做无限存储承诺，不自动删除用户数据或未核实回执。

## Owner API

下表统一以 `/api/v1/autonomy` 为前缀；读写均要求 owner，写入沿用 Origin/CSRF。UUID 由服务端实际记录取得，`expected_revision` 来自最新查询。模型没有策略、订阅、独立用例或归档管理权限。

| 方法与路径 | 请求/返回重点 |
| --- | --- |
| `GET /conversations/{conversation_id}/goals/{goal_id}` | 完整计划、机器验证状态、步骤、证据、检查点、恢复策略、订阅 |
| `PUT .../goals/{goal_id}/plan` | 上述 `GoalPlan`；初次 revision=0，后续保留原验收条件 |
| `POST .../goals/{goal_id}/checkpoints` | `expected_revision/step_id/status/evidence/note/remaining`；证据项为 `criterion_id/task_id` |
| `PUT .../goals/{goal_id}/policy` | `expected_revision/resume_after_restart/priority`，策略 revision 与计划 revision 独立 |
| `GET/POST /watches` | 查询订阅；创建需 `request_id/conversation_id/kind/target`，文件/设备需 `node_id`，可绑定 `goal_id` |
| `DELETE /watches/{watch_id}` | JSON `expected_revision`；停止并取消其未结束读取 |
| `POST /watches/{watch_id}/events` | 仅 external；`source_key/value`，value 最多 1,000 字 |
| `GET /events?after=0` | 最多 100 条持久事件及 `next_after` 游标；`value_json` 是数据 |
| `POST /events/{event_id}/ack` | 幂等确认显示过的通知；与目标是否消费事件分开 |
| `PUT/GET /plugins/{plugin_id}/business-suite` | `expected_revision/cases/rollback_on_failure`；返回用例与最近回退记录 |
| `GET /conversations/{conversation_id}/archive-preview` | 当前可归档摘要、行数和原文大小；会话先用既有接口归档 |
| `POST /conversations/{conversation_id}/archive` | `digest`；旧内容变化拒绝提交 |
| `GET /health` | 状态、观察时间、工作协程、容量、未知任务数与告警 revision |

原目标暂停/恢复继续使用 `/api/v1/plugins/conversations/{conversation_id}/goals/{goal_id}` 的既有控制接口。写操作冲突应重新读取状态，不自动改 revision 重试。

## 交给 DSH 的具体要求

按项目约定，本轮前端由用户直接控制 DSH。可交付以下工作单，不需要 DSH 修改 Core 的授权逻辑：

1. 目标详情展示固定验收条件、依赖步骤、真实任务链接、检查点和未完成事项；明确区分“机器断言通过”和“用户验收”。恢复开关默认关闭，展示剩余轮数、期限与最后暂停原因，策略变更带独立 revision。
2. 新建观察订阅表单支持四种来源、目标/设备范围、优先级、间隔、次数和期限；外部事件只描述当前配置的接入，不显示不存在的服务连接器。订阅建立后将实际 watch_id 关联展示给目标。
3. 通知中心按 `event_id` 增量读取、去重显示和确认；告警按 key+revision 去重，展示观察时间。事件值当作普通文本/JSON 数据，不作为指令或可执行 HTML。
4. 插件页面分别展示原样例、独立业务用例、基线比较、真实观察与回退；owner 编辑用例需明确保存，失败时保留候选差异和证据。不要把 `host_safety_verified=false` 改成安全标签。
5. 存储页展示热/冷大小与容量告警；在已归档会话上提供“压缩归档”预览，确认请求绑定 digest；恢复通过原取消归档操作。历史显示仍使用原 API，不在客户端自行解压或重写账本。
6. 验证登录/CSRF、陈旧 revision、停止后事件、重启后重复通知、未知执行、损坏归档和窄屏布局；Web 与 Windows 随包 UI 保持同一语义。后端冲突应保留用户输入并解释，不静默重试授权。

## 本地验证入口

专项用例为 `tests/test_autonomy_{goals,business,observations,storage,processes}.py`。进程测试运行两个独立本地 Core/Windows Node 进程、真实文件读取和重启，默认约 100 秒；将环境变量 `NEXUS_AUTONOMY_SOAK_SECONDS` 设为 `7200` 可运行两小时真实计时测试。测试只操作 pytest 临时目录，完成后停止测试进程；模型配置关闭，轮询不产生模型调用。沙箱比较单元测试明确使用模拟传输，不能作为本轮真实 runsc 验证证据。

发布前需分别核对 Core 与实际 Node 的目录和 `plugin_digest`。仅更新 Core 运行的 `builtin.goal`，且所有 Node 运行插件的 manifest/digest 保持一致时，可以先部署云端 Core：保留配置中与实际旧 Node 相符的指纹，不把云端新目录计算值替换进去。Node 回执压缩须在 Windows Node 自身升级后生效；云端包包含代码不等于设备已升级。迁移遵循原一致备份流程；032 与 Android 031 连续编号，发布包必须审查依赖资源，不根据本地文件存在推定获准发布。当前技术证据和未完成验收以路线图为准。
