## 验证方法与结果

通过正式 HTTPS owner 会话 API 提交自然语言，使用实际 `deepseek-flash` 模型、既有 Windows Node 和独立 runsc/KVM 沙箱。未注入模型返回、预制插件源码或伪造候选。缺口场景只给重复使用的目标和输入，让模型检查目录并选择能力形式；不是后台自行创建无关目标。

两个 Skill 的实际系统信息均为 Windows `10.0.26200`、AMD64、Python `3.13.9`。目录步骤返回 5 项、`truncated=false`，与配置 workspace 的直接只读枚举逐项一致。Core 实际在 Ubuntu，Windows 是执行 Node。

两个 Skill 运行均为 `succeeded / skill_steps_verified`，不是仅观察模型说“完成”。本轮共 6 个真实设备任务：两个插件调用、三个 Skill 子步骤，以及缺口 Skill 创建前模型自行选择的一次只读系统信息检查。逐一核对 Core task/attempt 与 Node 持久回执：任务、尝试和命令摘要匹配，输出一致，均只有 1 次派发、执行已停止且结果已确认。两个插件另有独立预期值断言；runsc 样例通过本身仍不等于任意业务输入正确。

## 失败、修复与费用

失败记录保留，不计作完整流程通过：

- 首次直接创建 `user.creation_machine_check`，模型遗漏嵌套输出对象的字段定义；保存候选后被可信 Skill 测试器拒绝，未批准、启用或执行。2 次调用，$0.005058。
- 首次缺口 Skill 请求使用现有契约不支持的 `default` Schema 关键字；原有参数反馈允许有界修正，但本轮仍未通过，没有生成版本或执行。4 次调用，$0.011528。
- 明确创建插件的前两次参数提交也被拒绝；模型在原有轮次限额内修正，随后创建、测试、启用并运行成功。

修复只补充既有契约指导：列明内置步骤实际结果字段、允许的 Schema 关键字、固定目录限额应直接写入参数，说明 Skill 使用 Core 分配的 revision。没有放宽 Schema 验证或增加重试额度。另修正创建结果的批准语义：`approval_required` 独立表示尚未获批，`approval_available` 表示测试已通过；失败不能被解释成无需批准。用新的真实请求验证修复，未覆盖旧候选或费用。

本轮 8 个会话轮次（6 次生成尝试＋2 次获批执行）合计 **26 次模型调用，65368 microunits，即 $0.065368**。生产原始账本按 `coalesce(chat_turn_id,work_root_turn_id)` 关联核对，均为 `completed / calculated`；这是按价格快照折算的记录，不是供应商账单对账。全局调用从 111 增至 137；原 5 笔未知费用保留，本轮未新增未知费用。

曾有模型说明误将 Node 系统信息称作 Core 环境，并在早期回复中混淆 Skill revision 与插件语义版本；上述报告以结构化记录为准。这些少量样例证明实际链路可用，不证明任意提示都能一次生成正确能力。
