# Windows / Android 前端：用户直接指挥 DSH 的工作说明

日期：2026-10-21。目标：为 NEXUS 建立 Windows App 与 Android App 前端。用户直接在 DSH 中选择模型、发送要求、决定方案和控制执行；Codex 提供交接与按需审查，不启动、托管或向 DSH 自动派发任务。

这是工作约定，不是第二份路线图。批准、实际进度与验收只维护在 [ROADMAP](ROADMAP.md#前端与-app-开发)；架构边界见 [ARCHITECTURE 第 17 节](ARCHITECTURE.md#17-web-前端与-app-设计边界)。本轮交付文档；下文实施步骤是用户选定方案后授权的模板，不代表 App 工程、依赖或认证变更已经批准。

## 1. 三方如何配合

| 参与方 | 负责什么 |
| --- | --- |
| 用户 | 直接控制 DSH；决定界面方向、技术路线、首版范围和工具链安装；批准重要边界变更及最终体验 |
| DSH | 调查前端与接口，提出方案；获准后实现双端页面、适配、客户端代码、自测和安装交付；如实报告失败与限制 |
| Codex | 准备工作说明；用户回来要求审查时，检查代码、接口、安全、状态语义和证据，提出修复建议；需要修改时按用户指令处理 |

DSH 开发期间由它作为本批范围的唯一写入者，包括新客户端公共组件、工程文件及锁文件。要求 Codex 验收前，先让 DSH 完成本批改动并停止编辑，避免互相覆盖。不需要两边自动发消息；在本聊天说“验收前端交付”即可。

## 2. 第一次在 DSH 中这样说

在 DSH 中打开 `E:\NEXUS`，发送下面的文字。先只分析，形成具体选择后再实施。

```text

不启动服务或访问生产。不要读取 var/、.env、凭证、私钥或私人数据库。
工作区有未提交改动，必须保留，不能 reset、clean 或覆盖。

请提交：
1. 现有可复用的界面和接口，以及双端接入的实际缺口。
2. 复用 Web、共享 UI 跨平台、分别原生开发的比较与推荐理由。
```

以当前实际工作区为准，不能只读旧 HEAD：已有 M5/M6/P45 代码及文档包含未提交改动。DSH 的模型费用、工程读取及服务选择由用户在 DSH 中控制；NEXUS 运行时的每日预算不代表 DSH 开发费用上限。

## 3. 方案中要决定什么

现有前端是 Core 同源提供的 HTML、CSS 和原生 JavaScript。先调查能否复用现有模块及接口，再决定是否重写。

| 路线 | 要说清的取舍 |
| --- | --- |
| 复用 Web UI，加双端客户端外壳 | 代码复用、WebView 差异、远程页面与本地打包页面的区别、认证、导航限制、安装及更新；Tauri 2 可作为待验证候选 |
| 共享 UI 的跨平台客户端 | Flutter 等候选可共享哪些代码，哪些功能需平台实现；页面重写量、新认证设计及维护工具链 |
| 双端分别原生开发 | 平台体验的具体收益，是否值得维护两套 UI、状态适配和测试 |

Tauri 和 Flutter 官方资料均列出 Windows、Android 平台目标；这只说明候选有相应支持，不代表 NEXUS 已接入。[Tauri 介绍](https://v2.tauri.app/start/)、[Flutter 平台支持](https://docs.flutter.dev/reference/supported-platforms)。选型时再核实版本、插件、安全存储、更新和构建要求。

认证是前提。`src/nexus/core/security/http.py` 使用会话 Cookie；登录和写请求检查 Origin，写请求另检查 CSRF，浏览器 WebSocket 也检查 Origin。原生 HTTP 客户端不能假装同源浏览器，不能借用 Node 身份。受限 WebView 加载受信 Core 页面与本地 UI 请求远程 API 是不同接入方式，必须分别验证。

若现有认证不适配，先提出缺口、备选设计及契约变化，由用户批准；不预设必须建设 OAuth/PKCE 等额外身份系统。不关闭 TLS 校验、放宽来源或向远程页面暴露本机执行桥。平台边界参考 [WebView2 安全](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/security)、[Android 本机桥风险](https://developer.android.com/privacy-and-security/risks/insecure-webview-native-bridges)、[Tauri 远程能力](https://v2.tauri.app/security/capabilities/)。

## 4. 首版页面与行为

| 页面 | 最少应有的内容 |
| --- | --- |
| 连接与设置 | Core 地址、登录/退出、连接与设备状态、版本、费用和隐私；切换 Core 不串用旧凭证或历史 |
| 聊天 | 会话列表、新建/重命名/归档、真实增量回复、停止、历史恢复、工具步骤及结果；保留上下文和外发范围提示 |
| 任务与审批 | 实际状态、动作/版本/参数与范围、审批期限、拒绝、取消、结果证据及未知状态 |
| 项目与记忆 | 会话/任务/待办，明确保存/替代/撤销记忆，逐轮选择及同意外发；不同项目不混用背景 |
| 能力 | 候选、测试、具体版本批准、启用/停用与运行证据；生成成功不等于已可用 |

桌面可用导航/会话列表、聊天及按需展开的上下文多栏布局；手机以单列聊天为主。先审阅草图再定视觉；覆盖键盘、触屏、软键盘避让、长文本/代码、焦点，以及加载、空白、错误、离线和登录过期状态。

必须区分停止模型回复、取消执行和暂停新派发。唯一 Core 管理任务、权限、记忆和费用，模型回答不替代执行证据。断线或重启后先同步，不自动重发付费请求、旧审批或未知结果动作；缓存只作有界展示。App 不持有模型密钥，不直接控制 Windows Node。

首版不默认加入 Android Node、无障碍控制、语音、录音、通知、提醒、任意文件访问或本机 shell；这些需求分别决定。

## 5. 选定方案后如何批准与推进

用户检查 DSH 提出的目录、工具链、依赖和认证影响后，可以一次批准边界清楚的首版，无需每个按钮再确认；新的安全、架构、重要依赖或范围变化才暂停受影响部分。

可以发送下列模板，把占位内容换成它刚提交的具体方案：

```text
采纳你提出的【方案名称】。
本次批准【明确页面/功能范围】及刚列出的【目录、工具链与依赖】；
【认证变更：明确列出，或写“本次不批准认证变更”】。
先验证双端安装与登录，再交付聊天闭环，随后完成本批页面。
普通实现细节自主处理；新的安全/架构/重要依赖变化先说明。
保留已有未提交改动，不改生产、不推送或发布、不扩大手机执行权限。
验证失败先修复；环境限制如实记录，不能改成通过。
完成后提供差异、构建/测试证据、安装说明及待验证项，更新 ROADMAP。
```

建议顺序：

1. **双端最小接入**：可安装和启动，可信 HTTPS 登录/退出与撤销，Core 切换、异常证书、断网和缓存清理。先用隔离测试环境，不默认为获准访问生产。
2. **真实聊天闭环**：发送、增量回复、停止、刷新/重启查历史；重复点击或断网不多建轮次或多调用。未获真实供应商外发同意时使用模拟服务，不能据此宣称真实模型通过。
3. **其余页面**：先任务/审批/取消/未知状态，再项目、记忆、能力及完整设置；复用原 Core 执行与恢复链路。
4. **固定版本交付**：Windows 和 Android 安装产物、版本及摘要、构建环境、依赖锁、安装/退出/升级说明；区分开发包与正式签名发布，签名秘密不入库。

工具链和依赖在选型批准后再加。Core、contracts、安全策略、数据库、部署和系统设置不因“前端需要”自动获得修改许可；接口缺口先提出最小变更及验证方式。客户端目录和语言尚未选定，不机械套用其他项目配置。
